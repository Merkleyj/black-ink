Information Security Policy

Black Ink (blackinkhq.com) · Operated by Jacob Merkley, sole proprietor · Version 1.0 · Adopted July 2026 · Reviewed at least annually

1. Purpose and scope

This policy documents how Black Ink identifies, mitigates, and monitors information security risks. It covers the Black Ink web application, its cloud infrastructure, third-party service integrations (including Plaid), and all user financial data handled by the service. Black Ink is operated by a single individual, who is responsible for every control described here.

2. System architecture and data flow

  • The client application is a static progressive web app served over HTTPS from GitHub Pages at blackinkhq.com. There is no self-managed server infrastructure.
  • All server-side logic runs on Supabase, a managed cloud platform hosted on AWS: managed Postgres for storage and serverless Edge Functions for bank-data integration.
  • All bank-aggregation API calls (Plaid) are made exclusively server-side by an Edge Function. The client never communicates with Plaid's API directly and never possesses Plaid credentials or access tokens.
  • Bank login credentials are entered only in Plaid's own hosted Link interface; Black Ink never sees, transmits, or stores bank usernames or passwords.

3. Access control

  • Administrative access to all infrastructure (Supabase, GitHub, Cloudflare, Plaid dashboard) is held solely by the operator, protected by unique strong passwords and multi-factor authentication.
  • End users authenticate through Supabase Auth (email/password with verification, magic link, or Google OAuth). Sessions use short-lived JWTs with automatic refresh.
  • Row-level security (RLS) is enforced on every database table. Each user can read and write only rows bound to their own authenticated user ID. Plaid access tokens are stored in a table with RLS enabled and no client access policies at all — they are reachable only by the server-side service role.
  • Server-side requests are authorized per-user: the Edge Function validates the caller's JWT before acting, and acts only on that user's data.

4. Data protection

  • In transit: all traffic — client to app, client to Supabase, server to Plaid — is encrypted with TLS (HTTPS). The production domain enforces HTTPS.
  • At rest: data resides in Supabase managed Postgres, encrypted at rest by the platform (AES-256 on AWS infrastructure).
  • Secrets: Plaid API credentials and service-role keys are stored in Supabase's encrypted secrets manager, are excluded from source control, and never appear in client code. The repository contains only the public anon key, which is protected by RLS and safe by design.
  • Data minimization: Black Ink stores only what the product needs — transactions, balances, and account metadata. Full account numbers, bank credentials, SSNs, and government IDs are never collected or stored. Financial data is used solely to display each user's own finances back to them; it is never sold or shared with third parties.

5. Change management and software integrity

  • All application code is version-controlled in Git with full history. Changes are reviewed and tested locally before deployment.
  • Deployments are reproducible: static hosting builds from the main branch; Edge Functions are deployed through Supabase's tooling.
  • Third-party dependencies are deliberately minimal (Chart.js, Supabase client, Plaid Link) and vendored or version-pinned; they are updated when security releases warrant.

6. Monitoring and incident response

  • Supabase provides authentication logs, database logs, and Edge Function logs, which are reviewed when anomalies are suspected; Plaid's dashboard provides API monitoring for the bank integration.
  • In the event of a suspected breach the operator will: (1) revoke and rotate affected credentials and tokens, including de-authorizing Plaid items; (2) assess scope using platform logs; (3) notify affected users by email without undue delay, with a factual description and recommended actions; (4) remediate the root cause before restoring service.
  • Because the platform surface is small (one static site, one database, one function), rotation and shutdown can be executed within minutes.

7. Data retention and deletion

  • Users may delete their transactions or their entire dataset at any time from within the app.
  • Deleting a user account cascades to all of that user's rows, including stored Plaid access tokens; linked bank connections are de-authorized with Plaid on unlink.
  • Users can export their complete data (JSON/CSV) at any time.

8. Physical security

Black Ink operates no physical infrastructure. Physical security of servers is inherited from the cloud providers (AWS via Supabase; GitHub; Cloudflare), each of which maintains industry-standard certifications (e.g., SOC 2) for their platforms. Operator devices used for administration are password-protected, kept updated, and used only by the operator.

9. Review

This policy is reviewed and updated at least annually, and whenever the architecture changes materially (for example, new data categories, new third-party integrations, or a move away from the current managed platforms).
